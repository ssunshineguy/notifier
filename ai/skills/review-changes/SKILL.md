# Review changes

1. Identify the task diff against its intended base, including staged, unstaged, and new files. Use the trigger table and [guard outcomes](../../../AGENTS.md#guard-outcomes) in `AGENTS.md`. Scope and README guards run for every diff, including prose-only changes and an unchanged README. When asked for all guards, account for each one and say which have no applicable changes.
2. Delegate `migration-guard` before applying changes in `notifier/db/migrations/` or `notifier/db/init/`, including via Compose. Run the relevant commands and record their results. Use `make check` for Go unit tests, vet, lint, format verification and diff whitespace checks. For changed PostgreSQL behavior, run `make test-integration`. For concurrency and lifecycle changes, add `go test -race ./...`. Use [generate-api](../generate-api/SKILL.md) when checking generated outputs. For Compose changes, run `docker compose config -q` and use [verify-local-api](../verify-local-api/SKILL.md) when runtime behavior changed. For every code change (including Python-only, tests, scripts, tooling and generated code), run `make test-e2e` (after explicit `make setup-e2e`) for the [API e2e suite](../../rules/tests.mdc#api-end-to-end-tests) with the intended Compose project and record the command, result and diff it verifies. Add or update scenarios for new behavior; existing scenarios can verify an authorized pure refactor. Smoke checks and unit tests do not replace this run. Also run checks appropriate to the changed language or tool. Run `make ai-check` for AI workflow changes. Prerequisites and dependency updates are in the [development guide](../../../docs/development.md).
3. Delegate the remaining applicable guards. Provide the repository root, comparison base, changed files, relevant behavior or approval context (including prior risk acceptances in this scope), and available test or regeneration evidence. For new condition types, include the per-layer change/N/A record from [add-endpoint](../add-endpoint/SKILL.md#new-condition-types). When a named guard is unavailable, ask a read-only reviewer to follow its `ai/agents/<name>.md` instructions. If delegation is unavailable, apply those instructions directly and label the review as such.
4. Resolve findings and recheck affected parts under the shared guard outcomes. A confirmed blocker leaves the task incomplete; each warn needs a fix or explicit human acceptance. Reuse prior acceptance of the same risk in this scope without relabeling it fixed. Reject false findings with evidence. Report each guard status, finding disposition, remaining accepted risks, README change/N/A rationale, and material verification gaps. Calculate the PR percentage only with the [PR coverage methodology](../pr-description/SKILL.md#test-coverage).
