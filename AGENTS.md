# Context for AI agents

## Service

Notifier sends an HTTP event to the client when a condition set by the client is met.
Architecture, sequence diagrams and prototype limitations are described in [README.md](README.md).

The service is a single `notifier` binary that runs in different modes:

| Mode | Purpose | Lifecycle |
| --- | --- | --- |
| `api` | HTTP notification creation and health probes | long-running process |
| `worker` | checks conditions and delivers events to clients | long-running process |
| `collector` | removes stopped notifications in batches | runs once and exits, started on a schedule |
| `migrate` | applies database migrations | one-off run before the services start |

## Language

- English: commit messages, PR titles and descriptions, branch names, code comments,
  OpenAPI descriptions, and everything written for AI agents (`AGENTS.md`, `ai/**`).
- Russian is allowed only in `README.md`.

## Task scope

- Keep the diff limited to the requested outcome and the changes needed to deliver it.
- Refactor existing code only when the user explicitly requests or approves the refactoring
  for this task. This applies even to code you already need to edit.
- Leave incidental cleanup and unrelated pre-existing issues for a separate task. If the
  request requires a refactor outside the approved scope, explain the dependency and ask first.

## Repository structure

Described in [README.md](README.md#структура-репозитория).

`make up` starts the test emulator alongside Notifier API. Host-side e2e tests
can reach it at `http://127.0.0.1:8081`. Services on the Compose network use
`http://emulator:8081`. To run it on its own, use `go run ./emulator/cmd/emulator`.
The emulator OpenAPI source lives in `emulator/api/spec/` and the runtime code
in `emulator/internal/`.

Both services serve `/health/live` and `/health/ready` on internal loopback
listeners. Notifier API uses port `9080` and the emulator uses `9081`.
Compose runs the readiness checks inside each container.

## Database

Follow `ai/rules/migrations.mdc`: naming, locks on existing tables, rerunnable statements, types.

- Everything lives in the `notifier` schema, never in `public`.
- `notifier/db/schema/*.sql` is generated by `make migrate`; read it to see a full table, never edit it.
- Roles live in `notifier/db/init`: `notifier_migrator` owns the schema and runs migrations; every mode has
  its own role (`notifier_api`, `notifier_worker`, `notifier_collector`) with its own DSN in the config.
  Mode roles get CRUD on all tables through default privileges, so migrations contain no grants.
- Queries for due notifications filter `stop_dt IS NULL AND next_scheduled_dt <= now()`:
  the partial index `ix_notification_next_scheduled_dt` is used only with both conditions.

## AI environment

`AGENTS.md` is the entry point. `CLAUDE.md` imports it. Edit rules, skills and guards in `ai/`.
With `python3` available, run `make ai-setup` after cloning, changing a guard, or adding, removing, or renaming AI files.
It links Claude Code rules, skills and agents under `.claude/`, links Codex skills under
`.agents/skills/`, and generates Codex agent definitions under `.codex/agents/`. These paths
are local setup output.
Use the rules linked above for the layer you touch.

## Guards

Delegate to the applicable read-only reviewers from `ai/agents/` after each logical unit.
Pass the user's task scope and explicit approvals, changed files, comparison base, and
relevant test evidence. Use the named agent or give a reviewer the corresponding Markdown
instructions.

| Guard | When |
| --- | --- |
| [`scope-guard`](ai/agents/scope-guard.md) | For every task diff. Checks that each change serves the requested outcome and any refactoring was explicitly authorized. |
| `architecture-guard` | After production Go changes in `notifier/`, `emulator/`, or shared `internal/`. Checks package boundaries, runtime I/O, PostgreSQL and safe logging. |
| [`go-guard`](ai/agents/go-guard.md) | After changes to handwritten Go code, including tests. Checks correctness, concurrency, reliability, security, and test coverage of changed behavior. |
| `api-contract-guard` | After OpenAPI, generated API, or observable HTTP behavior changes. |
| `test-coverage-guard` | After Go behavior, SQL, or Compose startup changes. |
| `migration-guard` | After changes to `notifier/db/migrations` or `notifier/db/init`, before applying them. |
| `comment-guard` | After adding or editing code comments. |
| `readme-guard` | After editing `README.md`. |

Review each blocker and warn against the task scope. Fix confirmed findings and rerun affected
checks. Report any agreed exception or unverified behavior at handoff.

## Keeping docs up to date

Update this file and the relevant `ai/rules/` when the folder structure, layer boundaries, run modes, or development commands change.

When a change affects `README.md`, propose the specific edit to the PR author and wait for
approval. An explicit request for a specific edit is approval for that scope. Add new content
only when the author explicitly asks for it.
