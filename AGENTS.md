# Context for AI agents

## Service

Notifier sends an HTTP event to the client when a condition set by the client is met.
Architecture, sequence diagrams and prototype limitations are described in [README.md](README.md).

The service is a single `notifier` binary that runs in different modes:

| Mode | Purpose | Lifecycle |
| --- | --- | --- |
| `api` | CRUD of notifications over HTTP | long-running process |
| `worker` | checks conditions and delivers events to clients | long-running process |
| `collector` | removes stopped notifications in batches | runs once and exits, started on a schedule |
| `migrate` | applies database migrations | one-off run before the services start |

## Layer boundaries

- `core` imports nothing from `internal/` and performs no I/O.
- `server/handlers` is a thin layer: parse the request → call the logic → write the response. No SQL or HTTP clients here.
- `storage` and `interactions` do not import `server`, `worker` or `collector`.
- `server/codegen` is generated from `api/bundle/openapi.yaml`; change it only through the spec in `api/spec/`.
- Dependencies are wired only in `application`.

## Database

Follow `ai/rules/migrations.mdc`: naming, locks on existing tables, rerunnable statements, types.

- Everything lives in the `notifier` schema, never in `public`.
- `db/schema/*.sql` is generated by `make migrate`; read it to see a full table, never edit it.
- Roles live in `db/init`: `notifier_migrator` owns the schema and runs migrations; every mode has
  its own role (`notifier_api`, `notifier_worker`, `notifier_collector`) with its own DSN in the config.
  Mode roles get CRUD on all tables through default privileges, so migrations contain no grants.
- Queries for due notifications filter `stop_dt IS NULL AND next_scheduled_dt <= now()`:
  the partial index `ix_notification_next_scheduled_dt` is used only with both conditions.

## Comments

Follow `ai/rules/comments.mdc`: default to no comment, write one only for a reason, a contract or a trap.

## AI environment

`ai/` is the source of rules, guards and skills; `make ai-setup` links it into `.claude/`
(rules become `.claude/rules/*.md`). Edit files in `ai/`, never in `.claude/`, and rerun
`make ai-setup` after adding or removing a file.

## Guards

Read-only reviewer subagents in `ai/agents/`. Call them after finishing a logical unit, passing the
list of changed files.

| Guard | When |
| --- | --- |
| `comment-guard` | After any change that adds or edits comments. |
| `migration-guard` | After adding or changing a file in `db/migrations` or `db/init`, before `make migrate`. |
