# Context for AI agents

## Service

Notifier sends an HTTP event to the client when a condition set by the client is met.
Architecture, sequence diagrams and prototype limitations are described in [README.md](README.md).

The service is a single `notifier` binary that runs in different modes:

| Mode | Purpose | Lifecycle |
| --- | --- | --- |
| `api` | HTTP notification creation and health probes | long-running process |
| `worker` | checks conditions and delivers events to clients | long-running process |
| `collector` | removes stopped notifications in batches | runs once and exits, started on a schedule |
| `migrate` | applies database migrations | one-off run before the services start |

## Language

- English: commit messages, PR titles and descriptions, branch names, code comments,
  OpenAPI descriptions, and everything written for AI agents (`AGENTS.md`, `ai/**`).
- Russian is allowed only in `README.md`.

## Task scope

- Keep the diff limited to the requested outcome and the changes needed to deliver it.
- Refactor existing code only when the user explicitly requests or approves the refactoring
  for this task. This applies even to code you already need to edit.
- Leave incidental cleanup and unrelated pre-existing issues for a separate task. If the
  request requires a refactor outside the approved scope, explain the dependency and ask first.

## Repository structure

Described in [README.md](README.md#структура-репозитория).

`make up` starts Notifier API, `notification_worker`, and the test emulator. Compose uses
the checkout directory name as the project name. For checkouts with the same directory
name, set a distinct `COMPOSE_PROJECT_NAME` in each local `.env`. Use a new project name
if the checkout would otherwise reuse the old `notifier` project.
`make up` prints the assigned loopback addresses for API, emulator and PostgreSQL.
Services on the Compose network use `http://emulator:8081`. To run the emulator on its own,
use `go run ./emulator/cmd/emulator`.
The emulator OpenAPI source lives in `emulator/api/spec/` and the runtime code
in `emulator/internal/`.

Notifier API, the emulator, and the worker serve `/health/live` and `/health/ready` on internal
loopback listeners on ports `9080`, `9081`, and `9082` respectively. Compose runs the readiness
checks inside each container and restarts the worker when it exits with an error.

## Database

Follow `ai/rules/migrations.mdc`: naming, locks on existing tables, rerunnable statements, types.

- Everything lives in the `notifier` schema, never in `public`.
- `notifier/db/schema/*.sql` is generated by `make migrate`; read it to see a full table, never edit it.
- Roles live in `notifier/db/init`: `notifier_migrator` owns the schema and runs migrations; every mode has
  its own role (`notifier_api`, `notifier_worker`, `notifier_collector`) with its own DSN file beside the shared config (`api.dsn`, `worker.dsn`, `collector.dsn`, `migrate.dsn`).
  The CLI reads only `<mode>.dsn`, or the file selected by `-database-dsn-file`. Compose mounts
  only that service's file as `/run/secrets/database_dsn`; DSN files are excluded from images.
  Checked-in DSN files are local development credentials matching `notifier/db/init` only.
  Mode roles get CRUD on all tables through default privileges, so migrations contain no grants.
- Local API e2e tests use `notifier_e2e` with the same object privileges as the mode roles.
  `make up` applies `002_e2e_role.sql` to existing PostgreSQL volumes as well.
- Queries for due notifications filter `stop_dt IS NULL AND next_scheduled_dt <= now()`:
  the partial index `ix_notification_next_scheduled_dt` is used only with both conditions.

## AI environment

`AGENTS.md` is the entry point. `CLAUDE.md` imports it. Edit rules, skills and guards in `ai/`.
With `python3` available, run `make ai-setup` after cloning, changing a guard, or adding, removing, or renaming AI files.
It links Claude Code rules, skills and agents under `.claude/`, links Codex skills under
`.agents/skills/`, and generates Codex agent definitions under `.codex/agents/`. These paths
are local setup output.
With Python 3.11 or newer (the development baseline is Python 3.14), run `make ai-check`
to check canonical metadata, local links, generated TOML and installed setup without modifying
the checkout. It generates temporary setups and checks drift and repeat generation.
Workflow fixtures need a separate Codex reviewer run; see [AI checks](ai/checks/README.md)
for the automated boundary, reviewer procedure and checker regression tests.
Use the rules linked above for the layer you touch.

## Guards

Delegate to the applicable read-only reviewers from `ai/agents/` after each logical unit.
Pass the user's task scope and explicit approvals, changed files, comparison base, and
relevant test evidence and prior human risk acceptances in this scope. Use the named agent or give a reviewer the corresponding Markdown
instructions. Pass the full diff to `comment-guard` so it can review deleted comments.

| Guard | When |
| --- | --- |
| [`scope-guard`](ai/agents/scope-guard.md) | For every task diff. Checks that each change serves the requested outcome and any refactoring was explicitly authorized. |
| `architecture-guard` | After production Go changes in `notifier/`, `emulator/`, or shared `internal/`. Checks package boundaries, runtime I/O, PostgreSQL and safe logging. |
| [`go-guard`](ai/agents/go-guard.md) | After changes to handwritten Go code, including tests. Checks correctness, concurrency, reliability, security, and test coverage of changed behavior. |
| `api-contract-guard` | After OpenAPI, generated API, or observable HTTP behavior changes. |
| `test-coverage-guard` | After any code change, including Python, tests, scripts, tooling and generated code, or SQL/Compose changes. Verify the mandatory e2e run even for behavior-preserving edits. |
| `migration-guard` | After changes to `notifier/db/migrations` or `notifier/db/init`, before applying them. |
| `comment-guard` | After adding, editing, or removing code comments, including in deleted files, or changing a decision protected by `DND:`. Check the full diff against the [DND policy](ai/rules/comments.mdc#protected-comments). |
| `readme-guard` | For every task diff, even when `README.md` is unchanged. Check drift caused by this change; a reasoned “no README change required” is valid. |

Run e2e for **every code change**, including Python-only, test, script, tooling and generated-code
changes. New behavior needs a new or updated scenario; an authorized pure refactor may use
existing scenarios. Follow [test rules](ai/rules/tests.mdc) and
[review-changes](ai/skills/review-changes/SKILL.md); prose-only changes do not require e2e.

## Guard outcomes

These rules apply to every guard and the final handoff:

- Every confirmed **blocker** blocks completion. Fix it and recheck; human acceptance of a
  warning cannot waive a confirmed blocker. If its fix is outside scope, report the dependency
  and leave the task incomplete.
- Every **warn** must be shown to the human task author and either fixed and rechecked or
  explicitly accepted by that human. Silence, an AI decision, or merely listing it in a report
  is not acceptance.
- Reuse an explicit prior acceptance for the **same risk in the same scope** without asking
  again. Record the decision reference or quoted approval and the remaining consequence.
  An accepted risk remains visible as **accepted**, never **fixed**. Changed risks or scope
  require a new decision.
- Evaluate findings against the approved task and decisions. Reject a false finding with
  concrete code, test or decision evidence; never silently drop it or downgrade its severity.
  A previously agreed behavior is not a new defect just because a reviewer prefers another design.
- Report each finding with its original severity, file/line, consequence, disposition
  (`open`, `fixed`, `accepted`, or `rejected`), and evidence. Only warnings may be `accepted`.
  For `fixed`, include the relevant recheck; for `rejected`, include the counter-evidence.
- Use **FAIL** while any blocker or warn is unresolved, **ACCEPTED** when only explicitly
  accepted warnings remain, and **PASS** when none remain (or all were fixed/rejected with
  evidence). **N/A** requires a trigger-based reason; scope and README reviews always apply.
  Keep `accepted`, `fixed`, and `rejected` findings distinct in the report. `info` is advisory.

## Business invariants

Use the [guarantee → code → verification table](ai/rules/architecture.mdc#business-invariants)
and its [test guidance](ai/rules/tests.mdc#business-invariant-verification). Code and tests are
the source of truth; targets linked to unfinished tasks are not implemented guarantees.
When implementing a target, update the implementation and verification links together.

Own production API successes use `200`; errors retain their contracted `4xx/5xx` responses.
The emulator may simulate external receiver responses, including `201`; see
[OpenAPI rules](ai/rules/openapi.mdc#operations).

A new condition type must account for contract → generation → domain → storage when needed →
worker/provider → emulator → tests → documentation. Record a change or a substantive N/A
for every layer using [add-endpoint](ai/skills/add-endpoint/SKILL.md#new-condition-types).

## Keeping docs up to date

Update this file and the relevant `ai/rules/` when the folder structure, layer boundaries, run modes, or development commands change.

When a change affects `README.md`, propose the specific edit to the PR author and wait for
approval. An explicit request for a specific edit is approval for that scope. Add new content
only when the author explicitly asks for it.
